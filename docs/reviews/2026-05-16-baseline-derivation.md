## 核心问题

1. **精度 baseline**：正确性判定的"真值（golden）"从哪来？`oracle_pytorch.py` 怎么产生、精度由什么保证？是否对上游 GPU Triton kernel 做过自动数值交叉验证？
2. **性能 baseline**：当前（移除 AscendC 后）性能参考 `t_ref` / `baseline_ns` 是什么、从哪来？speedup 比值是否在生效？

## 详细分析

### Q1 — 精度 baseline 怎么来的

**一句话**：精度真值来自 **AI/脚本按算子文档数学定义生成的 PyTorch oracle**（`oracle_pytorch.py::run`，`phase_b_oracle.py` 自述 "project-authored / Generated by scripts/phase_b_oracle.py"），按 `oracle_simplified` 三档分级，正确性 = 候选输出与 oracle 输出在 `tolerance_class` 窗口内 `allclose`。**它从未被自动与上游 GPU Triton kernel 做数值等价校验，也无人工专家 review**——所谓"GPU 双向交叉验证"在当前代码里是离线/概念，不是可执行 gate；代码中唯一的 review 信号是 "codex-review + self-diagnosis"（AI 审 AI）。

精度链条（构造而非证明）：

1. **kernel 冻结**（`phase_a_freeze.py`）：whole-file vendor 上游 GPU Triton 源 + 锁 commit/SHA。kernel 只是"被迁移对象 + 生成 oracle 时的参考阅读材料"，运行期评测**不执行** kernel。
2. **oracle 生成**（`phase_b_oracle.py`）三条路径：
   - **stub 路径**（默认/多数）：AST 解析 kernel 的 `@triton.jit` 签名，过滤 `*_ptr/*_stride/CONSTEXPR`，渲染 `run(inputs)->dict` 但 body `raise NotImplementedError` 指向 `contract.md` → 未就绪、不可评分；
   - **curated 公共数学集**：SiLU+mul / GELU+mul / softcap / layer_norm / rms_norm 等，从**公开数学定义**手写 PyTorch ref → `simple_pytorch_ok`；
   - **内嵌 body 表**（`phase_b_oracle.py:2645+` 的 `WORKING_REFS`，~50+ 任务）：逐任务的精确公式实现，作为 Python 源码字符串**内嵌在生成脚本里**，注释自称 "project-authored"——在本仓库（agentic-rl/kernel，由 Claude/codex 协作构建）语境下即 **AI 在前序会话生成**，非领域专家手写 → `formula_exact_manual`；
   - 5 个 `SKIP_TASKS` PoC（L1_01/L1_12/L1_16/L2_10/L3_04）oracle 不走自动化、单独维护——但同样无人工作者署名证据（`provenance.authors` 仍为泛化 `triton-ascend-bench team`）。
3. **三档可信度**（`validate_tasks.py:55`）：`simple_pytorch_ok`（公式良定义，直接 PyTorch 即对）→ `formula_exact_manual`（人工精确公式，需 review）→ `upstream_oracle_required`（公式不可简化/有未覆盖分支，需上游 oracle，**最弱**，含 scaffold 默认值，共 19 题）。Phase B 发现 kernel 有"会改变数学结果的未覆盖可选分支"时**诚实降级**到该档。
4. **精度的实际来源**（样本 `L1_12 rms_norm`）：① 人按公开定义重推数学（`y = x/sqrt(mean(x²)+eps)*w`）② oracle 内部 **fp32 累加**以对齐 kernel 内部精度 ③ 声明 `tolerance_class`（此处 `vector_reduce` atol/rtol=1e-3）界定可接受漂移窗口。三者合成即"精度 baseline"。
5. **没有的环节**：`scripts/` / `tests/` 内**无**任何脚本执行 `kernel.py` 并与 `oracle_pytorch.py` 输出做 allclose。`build_oracle_digest.py` 自述仅为"compact oracle↔kernel digest **for review**"（给人看的摘要，非 gate）。`test_oracles.py` 仅对少数 oracle 做 CPU 形状/数值点测，**不是**全库 oracle↔kernel 等价测试。

> **精度风险（修正版）**：迁移基准的核心命题是"忠于上游语义"，但 oracle 的正确性当前**仅靠 AI/脚本生成 + AI 自审（codex/self-diagnosis）+ tier 自报**支撑——**既无机器证明其等价于被迁移的 GPU Triton kernel，也无人工专家 review**。`formula_exact_manual`（74 题，占 81%）的精度上限 = 生成该 oracle 的 AI 对算子语义理解的正确性，无独立校验闭环；`upstream_oracle_required`（19 题）本质是"尚无可信 oracle"。**即真值（golden）本身是未经证明的 AI 产物**，这是整个基准最根本的 soundness 缺口（比"无机器交叉验证"更深一层：连"有人把过关"都不成立）。

### Q2 — 性能 baseline 怎么来的

**一句话**：**当前没有性能 baseline**。AscendC 已移除、`results/` 空、全仓库无任何 `t_ref`/perf baseline 数据源；`scoring.aggregate_perf` 对此显式返回 `perf_status="unavailable"`。speedup 公式 `s_t=baseline_ns/measured_ns` 是**休眠的预留槽位**；`cli.py analyze` 里流经 `baseline_ns` 的实际是提交者自报的 `aggregate_score`（correctness 衍生），并非性能测量——这是为保 `*_native` 输出 schema 稳定的 shim。

性能链条（缺失）：

1. **来源全无**：`validate_tasks.py:31,37` 注释明确移除 `ascendc_baseline.yaml`（"GPU-triton→NPU-triton *migration* benchmark; perf is not measured vs hand-written AscendC native"）；`find results`= **0 文件**；全仓库 grep 无 `perf_baseline / a2_latency / gpu_latency / measured_latency_ns` 任何赋值。
2. **scoring 诚实兜底**：`scoring.aggregate_perf`（`scoring.py:254-272`）—— 当无任何 `perf_measurable` 任务时返回 `{"perf_status":"unavailable","perf_status_reason":"no task has a defined performance baseline (AscendC removed; perf baseline deferred)", metrics:None}`，**不伪造 ε 塌缩数**（这是 codex P0-1/P0-2 的明确设计：区分"无基线"与"低分"）。
3. **公式休眠**：`s_t_value`（`scoring.py:98-117`）需要有限正的 `baseline_ns` 与 `measured_ns` 才算比值；二者当前都无真实来源 → 公式存在但不产出真实性能分。
4. **`baseline_ns` 槽位的实际内容**（`cli.py:673-696`）：`analyze` 读取提交 JSON 的 `aggregate_score` 作为 `baseline`，再 `measured_ns=1.0, baseline_ns=baseline`，使 `s_t = baseline_ns/measured_ns = aggregate_score`。即该字段被**复用**来承载"正确性衍生的聚合分"，与"性能"无关，仅为输出键名（含历史 `*_native` 命名）schema 稳定。
5. **本地不测性能**：`eval.py` 注释明确 "Timing/performance needs NPU hardware ... performance_status stays error here — never falsely ok"；`ShapeRunResult(..., measured_ns=None, baseline_ns=None)`。性能测量留待 910B verified runner（演进路线 Phase 3）。

> **性能风险/注意**：若外部 verified-results 文件谎报 `performance_status="ok"` + 有限 `aggregate_score`，`analyze` 会用这个被塞入的值算出"perf"——这是 schema 算术，不是真实基线。`*_native` 是兼容命名，与 AscendC 无关。

## 建议

| 优先级 | 建议 |
|--------|------|
| P0 | **精度（根因）**：真值（oracle）是 AI/脚本生成、无机器证明、无人工专家 review——这是基准 soundness 的根缺口。补"oracle↔kernel 离线等价 gate"：在有 GPU 环境跑 `kernel.py` 与 `oracle_pytorch.py`，对每个 public shape 断言 `allclose` 落在该 task `tolerance_class` 窗口内，过不了的不得进 score-eligible 集。把 PDF 的"双向交叉验证"从概念变成 CI gate——这是当前 `formula_exact_manual`(74，占 81%) 唯一可能的客观背书。 |
| P0 | **精度**：在 AI 等价 gate 落地前，对外口径必须显式声明"oracle 为 AI 生成、未经独立验证"，不得表述为"已验证正确性"；74 个 `formula_exact_manual` 至少抽样做人工专家复核并在 `provenance.authors`/`reviewers` 记录真实署名。 |
| P0 | **精度**：19 个 `upstream_oracle_required` 在文档/榜单显式标注"oracle 未就绪、不计分"，避免被误读为"已评测通过"。 |
| P1 | **性能**：在设计文档/对外口径中明确"当前 0 个性能 baseline，性能轴 unavailable"，不要让 `s_t`/`FastP_native`/`capped_geomean_native` 等键名让人误以为有性能排名；这些键当前承载的是 correctness 衍生分。 |
| P1 | **性能**：定义 `t_ref` 的来源方案（如 910B 上 torch-npu eager 延迟、或同卡 triton-ascend 自身 fp32 参考实现延迟），并设计防作弊（避免 `baseline_ns` 继续被 `aggregate_score` 复用造成语义混淆）。 |
| P2 | 把 `cli.py analyze` 里 `baseline_ns = aggregate_score` 的复用加显式注释/重命名，避免未来引入真实 perf 时语义冲突。 |

## 局限性

- 本分析为**静态源码取证**（开发机无 GPU/NPU），未运行评测；"无机器交叉验证"是基于全 `scripts/`+`tests/` grep 与逐文件确认得出 `[confirmed]`，但不能 100% 排除某处隐式路径——已尽力穷举。
- 代码在分析期间仍演进（`process_isolation.py` 等当日新增）；本报告为 2026-05-16 快照。
- 未逐一审计 74 个 `formula_exact_manual` oracle 的数学正确性——只能确认"机制上为 AI/脚本生成 + 仅 AI 自审、无自动等价 gate、无人工专家署名"，无法对单个 oracle 的精度对错下结论。
- **更正记录**：本报告初版误述为"人工撰写 + 人工 review"；经查 `phase_b_oracle.py:122`（"project-authored"）、`_HEADER`（"Generated by ..."）、`:2760`（"codex-review + self-diagnosis"）、全 `meta.yaml` 泛化 `authors`，确认 oracle 为 AI/脚本生成、无人工专家 review，已据实更正全文相关结论（精度风险因此比初版更严重）。
